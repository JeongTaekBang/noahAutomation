## 컨셉 — 세 가지

### 1. 원천은 두 개, NOAH 오더북과 같은 모양

NOAH 파워쿼리 `Order_Book`이 SO(수주)·DN(출고)·세금계산서 발행으로 오더북을 굴리듯, AX에도 같은 짝이 있다.

| | NOAH `Order_Book` | AX 오더북 (이 구현) |
|---|---|---|
| 수주 라인 | `SO_국내`·`SO_해외` | **IR** Item requirement — 생성일·수량·단가·상태 |
| 출고 | `DN_국내`·`DN_해외` | **IT** Item transaction — 출고 1건 = 1행 |
| 매출 인식(Output) | 세금계산서 발행월 / 선적월 | IT `Transaction status` = 청구 여부 |
| 지난 달 고정 | `close_period.py` 스냅샷 | `ax_orderbook.db` 저장 (우리 판 Table 50229) |

빌린 것은 **방식**이다. NOAH 데이터(DN 매출월 등)는 쓰지 않고, 숫자는 IR·IT로만 낸다.

### 2. AX 오더북은 '청구' 기준이다

AX의 Output은 **고객에게 청구한 달**이다. 그런데 IR의 `Invoiced`는 이름과 달리 **출고됨**이다 — 프로젝트 품목요구는
출고(패킹슬립)만 올려도 Invoiced가 되고, 고객 청구는 프로젝트 청구로 따로 한다(IR에 `Delivered` 라인이 0개인 것도
그래서다). 청구 여부는 **IT의 `Transaction status`에만** 있다.

| IT `Transaction status` | 뜻 | 오더북에서 |
|---|---|---|
| `Invoiced` | 청구됨 | Output |
| `Posted` | 출고됐지만 **청구 전** | End에 남는다 (출고 후 미청구) |
| `Adjusted` | 정정 | 뺀다 |

그래서 **End = 미출고 잔량 + 출고했지만 청구 전인 금액**이다. 82-15300.001(66.8M)은 3/30·6/19에 출고됐지만 청구가
안 돼 AX가 2026년 내내 End로 들고 있었다. 처음엔 'AX 누락'으로 봤지만 AX가 맞았다(사용자가 AX에서 청구 내역 확인).

### 3. 저장이 곧 마감이다

AX는 월말에 오더북을 한 번 계산해 **Table 50229에 저장**하고, 다음 달은 그 End에서 시작한다. 그래서 지난 달 숫자는
안 바뀌고, 그 뒤의 청구·취소·단가/수량 변경은 **그 일이 보인 달**로 들어간다. 우리도 같은 일을
`ax_orderbook/ax_orderbook.db` 하나로 한다.

IR·IT는 '지금 상태'만 담은 누적 export라서, 저장하지 않으면 지난 달을 되살릴 수 없다. 나중에 취소된 라인은
단가·금액이 0이고 취소일도 없다.

## 계산식

키 = **Project + Cost center + Prod/Dept(Revenue)**. 키 × 달마다 한 행이다(회계 Raw 48열 형식).

| 칸 | 정의 |
|---|---|
| Start | 직전 달 End. 기준선 P01만 **회계 P01 Start** |
| Input | 그 달 생성된 IR 라인(생성일은 UTC라 +9h = KST) × 수주월 환율 |
| Output | **청구 누계 − 이미 Output으로 인식한 누계** × 인식월 환율 |
| End | (라인 수량 − 월말까지 출고 수량) × 단가 × 수주월 환율 + 월말까지 출고했지만 청구 전(`Posted`)인 금액 |
| Variance | End − Start − Input + Output — 차액. AX도 같은 뜻이다(환율 재평가, 수주·청구 금액 차이, 지난 계산 뒤의 취소·변경) |

모든 행에서 `Start + Input − Output + Variance = End`가 성립하고, `Start(P) = End(P−1)`이다.

### Output을 '누계의 차이'로 구하는 이유

IT에는 **청구 날짜가 없다** — 지금 청구돼 있는지만 있다. 그래서 묶음(**프로젝트 | 라인번호 | 품목번호**)마다 지금까지
청구된 누계를 저장해 두고, 다음 달에 새로 뽑은 IT의 누계에서 뺀다. 그 차이가 **그 달에 청구된 것**이다.

```
P10 마감 (11/02 추출)    10/29 출고 라인 = Posted    → P10 End에 남는다, 청구 누계에는 없다
P11 마감 (12월 초 추출)   같은 라인 = Invoiced        → 청구 누계 증가분 = P11 Output   (AX도 P11)
청구 뒤 크레딧 노트        누계가 줄어든다             → 음수 Output
```

기준선(아래) 안에서는 같은 추출본의 지난 달 말 누계를 빼므로 '그 달 출고분 중 지금 청구된 것', 즉 **출고월**
인식이 된다. 저장한 뒤부터는 AX처럼 **청구한 달**이다.

## 기간과 저장소

```
저장소가 비어 있음 ──기준선──────▶ P01 … P09 Closed · P10 Open   (추출본 하나로 P01~P10을 한 번에)
P10 Open ────────P11 계산·저장──▶ P10 Closed · P11 Open          (Start = 저장된 P10 End)
P11 Open ────────P11 다시 계산──▶ P11만 바꿔 넣는다               (AX의 Last calculated)
Closed 달 다시 계산 / 달 건너뛰기 ──▶ 거부
```

- **기준선** — 저장소가 비었을 때 한 번 한다. 같은 IR·IT로 P01부터 마감월까지 NOAH `Order_Book`처럼 굴린다.
  **마감 직후 추출본으로 만들어야 한다.** 12월 추출본으로 P10 기준선을 만들면 11월의 취소·청구가 기준선 안에 섞인다.
- **새 달** — 저장된 직전 달 End(키별 Raw)와 청구 누계에서 시작한다.
- **다시 계산** — 마지막 달만 Open이라, 같은 달을 다시 돌리면 다시 계산해 바꿔 넣는다. 실측: 같은 추출본으로 P10을
  다시 계산한 결과가 기준선과 원 단위로 같았다.
- **처음부터 다시** — 저장소 파일을 지운다(또는 `--store 다른파일.db`).
- 저장소에는 표가 셋 있다. `periods`(달마다 상태·방식·계산 시각·계산한 사람·IR/IT 파일·추출일·행 수), `rows`(Raw 행),
  `billed`(청구 누계 — 마지막 달과 그 앞 달 것만). OneDrive 폴더라 WAL을 쓰지 않는다.

### 기준선만의 정의 두 가지 — 지난 달이 회계와 갈리는 이유

IR은 지금 상태라서 기준선 안의 지난 달은 지금 데이터로 계산된다.

- **취소 주문은 처음부터 뺀다** — 회계는 취소한 달에 Variance로 뺀다. 그래서 지난 달 End가 회계보다 작다
  (P09 −597M 중 557M이 10월 취소 2건).
- **청구 날짜를 모르니 출고월로 인식한다** — 월말 출고·다음 달 청구분은 Output이 한 달 앞선다.

저장한 뒤부터는 둘 다 AX와 같다. 취소는 취소가 보인 달의 Variance, Output은 청구한 달이다.

## 회계 오더북은 어디에 쓰나

숫자는 IR·IT로만 낸다. 회계 파일(`Sales order book_MM_YYYY.xlsx`)은 세 군데에만 쓴다.

1. **기준선 P01 Start**(키별) — 기준선에는 P01 행이 있는 그 해 파일이 필요하다.
2. **키 매핑·Raw 속성** — 자재 부서 → 매출 부서(Prod/Dept Revenue), Cost center, 그리고 IR에 없는 Market·Industry·
   Order Book Code·Account Manager 등. 처음 보는 부서는 규칙(1000~1799 −900, 18xx −1000)으로 추정해 확인목록에 올린다.
   다음 달 계산에는 지난 해 파일도 된다.
3. **대조** — 같은 달 행이 있으면 차이와 원인을 붙인다. 없으면 그 달은 우리 숫자만 나온다.

회계가 수식으로 채우는 14열(Key·Category·Restate 등)은 비워 둔다 — 붙여 넣은 뒤 위 행의 수식을 끌어내리면 된다.
**계산 대상을 키로 거르지 않는다.** 예전엔 회계 Start에 있는 키만 계산하다가 크레인 등 9.4M이 조용히 빠졌다.

## 환율

| | 쓰는 환율 |
|---|---|
| Input·End | **수주월** 환율 — 외화 잔고를 매달 재평가하지 않는다. 환차는 Output 달의 Variance로 간다 |
| Output | **인식월** 환율 |

- M월 환율은 그룹 마감환율 파일 **'Closing rates - P{M−1}'**의 (KRW/GBP) ÷ (통화/GBP)다. P10 파일은 11월에 쓴다.
- 우선순위: 직접 입력(`--fx`) > 마감환율 파일·`fx_history.csv` > NOAH FX 시트(`sync_db.py`로 DB) > 역산 시드.
- Finance Hub에는 **지금 파일 하나만** 남는다. 그래서 읽은 값을 `ax_orderbook/fx_history.csv`에 쌓는다.
  P11 계산에 쓸 11월 환율(P10 파일)은 이미 쌓여 있다.
- **저장한 달의 End를 매긴 환율은 다음 달에도 같아야 한다.** 그래서 `--fx`로 넣은 값도 이력에 남긴다. 안 남겼더니 10월 JPY가
  빠져 11월 계산에서 82-15517.001에 가짜 Variance +1.1M이 났다.
- IR `Net amount`는 **거래통화**인데 통화 열이 없다. 그래서 외화 거래처 목록(코드)과 `ax_orderbook/통화지정.csv`
  (주문 단위 예외 — 예: 82-17677.001 EUR)로 통화를 정한다. 이 파일이 빠지면 외화 주문이 조용히 원화로 계산된다.
- 2025년에 생성된 외화 라인의 수주월 환율은 NOAH FX 시트에 그 달 열을 더해 넣는다(**EUR 2025-12는 아직 없다**).

## 매달 할 일

1. **다음 달 1~7일 중 같은 날** AX에서 두 개를 뽑는다.

   | 파일 | AX 화면 | 필터 (하나만) | 이름 |
   |---|---|---|---|
   | IR | Item requirement | Show = **All**, Created date `01/01/2024..` | `Item requirement_YYYYMMDD.xlsx` |
   | IT | Item transaction | Project date `01/01/2024..` | `Item transaction_YYYYMMDD.xlsx` |

   - `01/01/2024..` = 2024-01-01 이후 전부. 2026 오더북에서 가장 오래된 프로젝트가 2024-01-08에 생성됐으니 빈틈이 없다.
     필터를 더 깎지 않는다 — 조건을 늘릴수록 조용히 0건이 나는 위험이 커진다.
   - 둘 다 **누적 전체** export다(증분이 아니다). 지난 달과의 차이는 저장소가 계산한다.
   - 이름 끝 `_YYYYMMDD`는 추출일이고, CLI가 이것으로 점검한다. IR·IT 날짜가 다르거나 그 달이 끝나기 전이면
     **저장을 거부**한다. 마감 뒤 8일째부터는 경고한다 — 그 사이의 청구·취소가 이 달로 섞인다(AX는 다음 달로 간다).

2. 그 달 폴더 `ax_orderbook/2026/P11/`에 넣는다. 거기 없으면 `ax_orderbook/` 바로 아래도 보지만, 다른 달 폴더는 안 본다.
3. NOAH FX 시트 환율을 고쳤으면 먼저 `create_po.bat` [8] DB Sync를 돌린다.
4. `create_po.bat` → **[A]** → **[1] 미리보기**로 숫자를 보고 → **[2] 계산하고 저장**. 첫 줄에 이번 실행이 무엇인지 나온다.
   ```
   [1/4] 새 달 2026 P11 계산 — Start = 저장된 2026 P10 End · 저장하면 2026 P10 닫힘(Closed)
   ```
5. 결과는 `ax_orderbook/2026/P11/AX_오더북_2026_P11.xlsx`와 같은 이름의 `.html`이다(HTML은 Edge에서 더블클릭).
6. 회계 P11 오더북이 오면 `ax_orderbook/` 아래 아무 데나 두고 **P11을 다시 계산**한다. P11이 Open일 때(P12를 저장하기 전)만
   된다. 같은 추출본이면 프로젝트 숫자는 그대로이고, 회계 대조·차이 원인과 새 파일의 매핑·속성이 채워진다.

확인목록에 '환율 없음'이 뜨면 NOAH FX 시트에 더하거나, CLI에서 `--fx 통화=환율`(다른 달은 `통화=YYYY-MM=환율`)로
넣는다 — 메뉴에는 이 옵션이 없다.

```
      ├─ AX_오더북_2026_P11.xlsx

```

| 확인목록 | 사람이 볼 것 — 신규 키(속성 입력 필요), 큰 Variance(1천만 원 이상), 수주·청구 금액 차이, IR 라인 없는 IT 출고, 통화 확인, 부서 매핑 없음/규칙 추정, 환율 없음 |
| 라인내역_Pxx | 마지막 달의 라인별 계산 |
| 환율 | 쓴 환율과 출처 |

HTML은 같은 내용을 탭 여섯 개(요약·오더북·차이 원인·출고 후 미청구·확인목록·정보)로 보여 준다. 위쪽 공통 필터(기간·
Market·Order Book Code·Cost center·검색)가 모든 화면에 같이 걸리고, 막대나 행을 누르면 그 프로젝트·원인으로 내려간다.
회사 PC라 서버도 인터넷도 없이 열리도록 데이터와 차트 엔진을 파일 안에 넣었다(약 6MB).

### 차이는 항등식으로 읽는다

차이도 같은 항등식을 따른다: **ΔEnd = ΔStart + ΔInput − ΔOutput + ΔVariance**. P01~P10 누계(우리 − 회계)로 보면:

| | 우리 − 회계 | 주된 이유 |
|---|---|---|
| Start (P01) | 0 | 기준선 P01 Start = 회계 |
| Input | −851,728,489 | 취소 주문 −860.7M — 우리는 처음부터 빼고, 회계는 넣었다가 취소한 달에 Variance로 뺀다 |
| Output | −55,956,148 | 2025-12 출고·2026-01 청구분 −54.3M(82-15101.001 등) — 기준선은 출고월로 인식 |
| Variance | +797,452,345 | 위 Input·Output 차이를 되받는 쪽 |
| **End (P10)** | **+1,680,004** | = 0 − 851,728,489 + 55,956,148 + 797,452,345 |

다섯 줄을 그대로 더한 −108,552,288에는 아무 뜻이 없다.

## 차이 원인

회계와 갈리는 곳이다. 달·키마다 차이가 1원을 넘으면 표의 위에서부터 처음 맞는 원인을 붙인다(`classify_differences`).
이 표는 `ax_orderbook.DIFF_CAUSES`와 순서까지 같다 — `tests/test_ax_orderbook.py`가 대조하니, 원인을 더하면 표에도 한 줄.

| 원인 | 뜻 |
|---|---|
| **회계 조정** | 회계가 그 키의 Start를 손으로 고쳤다(회계 Start ≠ 회계 직전 달 End) |
| **취소 주문(회계는 그달 Variance)** | 그 달 흐름은 같고 Start·Variance만 다르다 — 회계는 취소한 달에 빼고 우리는 처음부터 뺐다 |
| **지난 달 차이 이월** | 그 달 Input·Output·End는 같다 — 지난 달까지의 차이가 Start로 넘어왔다 |
| **키 갈림** | 프로젝트 합계는 같고 키(Cost center·부서)만 다르다 |
| **청구 월** | Output 차이가 앞뒤 달과 상쇄된다 — 기준선은 출고월, AX는 청구월(월말 출고·다음 달 청구) |
| **취소 주문(처음부터 제외)** | 우리 End가 작고 그 프로젝트에 취소 라인이 있다 |
| **수주 사후 변경(IR은 지금 값)** | End 차이가 Input 차이로 설명된다 — IR은 바뀐 지금 값, AX는 수주 당시 값으로 넣고 바뀐 달에 고친다 |
| **기초 차이** | P01 — 회계 P01 Start와 IR·IT가 본 전년 12월 말 잔고의 차이 |
| **환율** | 외화 키의 환율 차이 |
| **기타** | 위 어디에도 맞지 않는 차이 |

'청구 월'·'취소 주문'·'수주 사후 변경'은 기준선의 정의에서 나온다. 저장한 뒤의 달에서는 줄어야 한다.

## 실측으로 알아낸 AX의 동작

이름만 보고 짐작하면 틀리는 것들이다. 데이터로 재고, 뜻은 AX 조회나 사람이 남긴 기록으로 확인했다.

- **IR `Invoiced` = 출고됨**(위). IR에는 청구일·청구번호 열이 없다 — 숨기기 전 원본 69열에도 없다.
- **IT `Posted`는 라인 합계로 본다.** 크레딧 노트·반품은 음수 `Non-Invoiceable` Posted 행으로 상쇄된다(82-12893.001).
  속성으로 먼저 거르면 상쇄 행이 빠져 없는 미청구가 생긴다. 수량과 금액이 둘 다 남아야 청구 대기다.
- **IR 라인번호를 재사용한다**(1,902쌍). 출고(IT)는 단가가 맞고 출고일 이전에 생성된 라인에 붙인다.
- IR `Created date`는 **UTC**다(+9h). `Net amount`는 **거래통화**다.
- 취소 라인은 단가·금액이 0이고 취소일이 없다 → 과거 달을 재현할 수 없다(그래서 저장한다).
- 월 1회 계산서 거래처(25일 마감)의 월말 출고분은 다음 달 계산서 = AX 다음 달 Output이다. NOAH `DN_국내` 비고에
  사람이 '실제 출고일'을 적어 둔 기록으로 확인했다.
- 자재 부서 → 매출 부서는 산술식 하나가 아니다 — 회계 파일에서 배우고 규칙으로 보충한다.
