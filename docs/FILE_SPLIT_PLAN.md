# 연도별 파일 분리 계획 (2026 → 2027)

> 작성: 2026-06-04 (대비 메모) | 갱신: 2026-10-02 (실행 결정 · 이동 → 복사) | 상태: **예정** — 2027년 1월 중순 실행

2026년이 끝나면 `NOAH_SO_PO_DN.xlsx`를 연도별 파일로 나눈다.
- **2026 파일은 손대지 않는다.** 연말 마감 장부로 그대로 남는다.
- **새 파일에는 진행 중인 것(재고)만 복사하고, 끝난 거래(흐름)는 넘기지 않는다.**
- **DB는 연도 파일을 전부 합쳐 읽어서 전 이력을 그대로 유지한다.**

회계 연말 마감 때 잔액만 다음 해로 넘기고 거래 내역은 그 해 장부에 두는 것과 같은 발상이다.

---

## 왜 하는가

- **행 수 피로 (2026-10-02 결정의 직접적 이유).** 한 해치가 쌓이면서 입력하고 찾는 일이 지친다.
  필터로 줄일 수는 있지만 열 때마다 다시 걸어야 하고, 공유 파일이라 필터 상태가 다른 사람과 섞인다.
  파일이 무거워지는 문제(XLOOKUP·배열 수식 재계산, 파워쿼리 새로고침, OneDrive 동기화)는
  행 수에 비례해 해마다 쌓이므로 분리해야만 줄어든다.
- **이어 써도 코드 수정은 필요하다.** PO `Status`의 `Invoiced P{XX}`에는 연도가 없다.
  한 파일로 2027년에 들어가면 1월에 `create_dn P01`을 돌렸을 때 2026년 P02~P12 라인을
  '아직 정산 안 된 라인'으로 본다 (`dn_recorder.invoiced_statuses` / `settled_statuses`).
  그래서 실제 비교는 '연도 처리 + 매일 필터'와 '연도 처리 + 1년에 한 번 이관'이다.
- **분리해도 잃는 게 거의 없다.** 1년 사이에 이력은 SQLite DB와 대시보드가 맡게 됐다.
  Excel은 '지금 진행 중인 일을 올려 두는 작업대'만 하면 된다.

> 옛 메모(2026-06)는 '충돌 사본 / 저장 10초 이상 / 30MB 이상' 신호가 올 때까지 단일 파일을 유지하고,
> '2년 시한 시스템에 분리는 과설계'라고 봤다. 신호보다 사람의 피로가 먼저 왔고, 위 두 번째 항목 때문에
> 이어 쓰는 것도 공짜가 아니라는 점이 드러나 결론이 바뀌었다.

## 왜 '이동'이 아니라 '복사'인가 (2026-10-02 결정)

처음 안은 이월한 행을 2026 파일에서 **지우는** 것(이동)이었다. 두 파일을 합쳐 읽을 때 같은 행이
양쪽에 있으면 수주가 두 번 잡히기 때문이다.
그런데 그렇게 하면 이월한 SO의 Input이 2026 파일에서 빠진다. 그 결과 **2026 파일의 파워쿼리
Order_Book에서 2026년 월별 Input과 Ending이 줄어든다.** 2026년을 Excel로 볼 방법이 사라지는 것이다.

그래서 2026 파일은 그대로 두고 **새 파일로 복사만** 한다. 대신 중복은 DB 동기화가
**이월 목록**으로 처리한다 (아래 'DB 동기화 수정' 참고). 덤으로 2026년 대사 재실행이나 문서
재발행은 2026 파일을 그대로 읽으면 된다 — 이월한 행도 원래 Status(`Invoiced P11`) 그대로 남아 있다.

## 무엇을 넘기나 (이월 기준)

**기준일은 2026-12-31이다.** 전환은 1월 중순이고 그 사이 1월 입력은 2026 파일에 계속 쌓이는데,
'전환하는 날 기준으로 열린 것'을 고르면 **12월 말에 열려 있다가 1월 초에 끝난 건**이 빠진다.
그러면 그 건의 1월 출고·매출이 2027 파일에 없어서 2027년 1월 Order Book과 `reconcile_so P01`에서
사라진다. 그래서 **'2026-12-31에 열려 있었던 것 + 그 뒤에 생긴 것 전부'**를 넘긴다.

**판단은 SO 라인 단위로 하고, 넘길 때는 그 라인에 딸린 행을 전부 함께 넘긴다.**

| 시트 | 새 파일에 넘길 것 |
|---|---|
| `SO_국내` / `SO_해외` | (a) **2026-12-31에 안 끝난 라인** — 그날까지의 DN으로 출고가 다 안 됐거나, 그날까지 매출이 인식되지 않은 DN이 딸린 라인. (b) **2027년에 등록된 라인** (`Period` ≥ 2027-01). (c) **2027년 날짜의 DN이 붙은 라인** (반품·재출고·단가 정정 등). `Hold`는 넘기고 `Cancelled`는 뺀다 |
| `PO_국내` / `PO_해외` | 넘기는 SO 라인에 연결된 PO 행 **전부**. 그리고 전환 시점에 `Invoiced`·`Cancelled`가 아닌 행(Status가 빈 행 포함). **분할 행 그룹(같은 `PO_ID + Line item`의 여러 행)은 통째로** |
| `DN_국내` / `DN_해외` | 원칙적으로 넘기지 않는다. 넘기는 SO 라인에 딸린 DN 행만 함께 넘긴다 (대부분은 1월 출고분이거나 아예 없다). **분할 행 그룹은 통째로** |
| `PMT_국내` | 넘기는 SO에 붙은 선수금 (아직 출고로 소진되지 않은 것) |
| `Customer_국내` / `Customer_해외`, FX | **통째로.** 기준정보라 재고/흐름 구분이 없다 |
| 파워쿼리 결과·피벗 시트 | 파일을 복사해서 만들면 그대로 따라온다 — 새로고침만 하면 된다 |

대부분의 라인은 '순수 미출고'라서 딸린 것이 미정산 PO 행뿐이다.
즉 대부분은 직관 그대로 **SO 미출고 + PO 미정산**이 되고, 아래 두 예외만 DN 행을 함께 끌고 간다.

### 예외 ① 매출 미인식 DN — 흐름처럼 보이지만 재고다

Order Book에서 Backlog는 '미출고'가 아니라 **'매출 미인식'**이다.
국내 DN 중 `세금계산서 발행일`이 빈 행, 해외 DN 중 `선적일`이 빈 행은 아직 Backlog 안에 있다.
그 DN을 SO 라인과 함께 넘긴다. SO 라인 없이 DN만 넘기면 새 파일에서 DN의
`Item`·`Unit Price` XLOOKUP이 SO를 못 찾는다.

12월 월합분은 대개 12월 말일자로 발행되고, 전환 전에 2026 파일에서 발행일을 채운다.
그러면 12-31 기준으로 인식된 매출이라 이 예외에 걸리지 않는다.

### 예외 ② 부분출고 라인 — 수량을 잔량으로 고쳐 넘기지 않는다

출고 여부와 잔량은 전부 `SO 수량 − DN 누계`로 계산한다
(납기현황, 대시보드, 파워쿼리 `SO_통합[출고완료]`, `create_dn` 잔량, `_billed_beyond_dn`).
10개 중 4개가 나간 라인을 DN 없이 넘기면 새 파일에서는 잔량이 10으로 보인다.

- ✅ **그 라인의 DN 행과 PO 행(계산서 처리된 행 포함)을 함께 넘긴다.** 계산이 그대로 유지된다.
  함께 넘긴 2026년 `Invoiced P11` 같은 행은 **새 파일에서만** 연도를 붙인다 → `Invoiced 2026-P11`
  (2026 파일은 원래 값 그대로. 아래 코드 수정 참고).
- ❌ **SO 수량을 잔량 6으로 고쳐 넘기지 않는다.** 같은 행(PK `SO_ID + Line item`)이라 DB는 이를
  '수량 10 → 6 변경'으로 받는다. 그러면 2026년 수주금액이 소급해서 줄고 Order Book에 Variance로 터진다.

> 옛 메모의 '라인 잔량 단위로 잔량만큼만 이월'은 바로 이 ❌ 방식이라 폐기했다.

## DB 동기화 수정 — 연도 파일을 합쳐 읽는다

지금 `sync_db.py`는 엑셀에 없는 행을 DB에서 지운다 (`db_sync.py` prune 단계, FX도 마찬가지).
**새 파일만 읽으면 첫 동기화에서 2026년에 끝난 SO·PO·DN·선수금과 2026년 환율이 DB에서 삭제된다.**

```
지금:     NOAH_SO_PO_DN.xlsx ────────────────────────────→ 행 추가·수정 → 없는 행 삭제 → DB

바꾼 뒤:  NOAH_SO_PO_DN_2026.xlsx − 이월 목록에 있는 행 ┐
          NOAH_SO_PO_DN.xlsx(현재)                      ┴→ 시트별로 합침 → 행 추가·수정 → 없는 행 삭제 → DB
```

- **연도 파일을 전부 읽어 시트별로 합친 뒤, 기존 처리(추가·수정·삭제)를 그대로 돌린다.**
  삭제 로직을 그대로 두므로 2026 파일의 끝난 행을 나중에 고쳐도 DB에 반영된다.
- **이월 목록** (`NOAH_SO_PO_DN_2026_이월목록.csv`, 2026 파일 옆): 전환할 때 새 파일로 복사한 행의
  키를 적어 둔다. 동기화는 **2026 파일에서 이 목록의 행을 건너뛴다** — 이월된 건의 주인은 2027 파일이다.
  DB를 다시 만들어도 남고 사람이 열어 볼 수 있게 DB가 아니라 파일로 둔다.
- **왜 '같은 키면 새 파일 우선'이 아니라 목록인가:** 2027년에 이월된 건의 라인을 지우거나
  `Line item` 번호를 바꾸면 그 키가 새 파일에서 사라진다. '새 파일 우선'이면 그때 2026 파일의
  옛 행이 다시 DB에 살아나 **이중으로 잡힌다** (번호 바꾸기는 실제로 자주 있다 — sync_log의
  '삭제'는 대부분 재키잉이다). 목록이 있으면 2026 쪽 사본은 무슨 일이 있어도 무시된다.
- **겹침 검사:** 목록에 **없는** 2026 행의 키가 2027 파일에 있으면 동기화를 멈추고 목록을 보여 준다.
  목록 밖에서 손으로 복사한 행이 수주를 두 번 잡는 것을 막는다.
- **`_row_seq`는 파일마다 따로 매긴 뒤 합친다.** 분할 행 그룹을 통째로 넘겨야 두 파일의 순번이 같아진다.
  그룹 일부만 넘기면 새 파일에서 순번이 앞당겨져 **남의 행(PK)을 덮는다** — 전환 스크립트가 막는다.
- **지난 연도 파일은 이름 규칙으로 자동으로 찾는다**: 데이터 폴더의 `^NOAH_SO_PO_DN_(\d{4})\.xlsx$`.
  내년에는 이름만 바꾸면 되고 설정은 건드리지 않는다. OneDrive 충돌 사본(`-PC이름`)이나
  백업 사본(`_YYYYMMDD_HHMMSS`)은 이 패턴에 걸리지 않게 엄격하게 잡는다.
- **FX는 현재 파일에서만 읽는다.** 새 파일에 통째로 넘어가 있다.
- **성능**: 동기화할 때마다 옛 파일을 한 번 더 읽어 몇 초가 늘어난다. 해가 쌓여 느려지면
  '수정 시각이 안 바뀐 파일은 캐시로 읽기'를 붙인다. 지금은 하지 않는다.

**옛 메모의 두 안을 고르지 않은 이유:**
- (A) '파일마다 자기 연도 행만 prune' — 이월한 행은 `SOD-2026-*` ID를 단 채 새 파일에 있으므로
  ID 연도로는 파티션을 나눌 수 없다. 이월 목록이 그 역할을 더 정확하게 한다.
- (B) '옛 파일은 동기화에서 빼고 스냅샷만' — 2026 파일의 끝난 행을 나중에 고쳐도 DB에 안 들어가고,
  끝난 연도의 라인 단위 내역을 대시보드에서 볼 수 없다.

## 다른 도구에 미치는 영향

| 도구 | 읽는 곳 | 할 일 |
|---|---|---|
| 대시보드, `close_period`, 스냅샷 | DB | 없음 — 자동으로 전 연도를 본다 |
| `create_dn`, `delivery_status`, 문서 생성(`create_*`) | 현재 파일 | 없음 — 진행 중인 일은 전부 현재 파일에 있다 |
| `dn_recorder` | 현재 파일 | **연도가 붙은 `Invoiced 2026-P{XX}`를 '정산 완료'이자 '계산서 처리됨'으로 센다** (`settled_statuses`, `_billed_beyond_dn`) |
| `reconcile_po` / `reconcile_so` / `reconcile_ind` | 현재 파일 (고정 경로) | 2027년 기간은 그대로. 2026년 기간 재실행은 2026 파일을 가리키기만 하면 된다 (`--year 2026` 정도) |
| 동료 PC (GUI·콘솔 메뉴) | `noah_config.ini`의 경로 | 없음 — 현재 파일 이름을 유지하므로 |
| 2026 파일의 파워쿼리 `Order_Book` | 2026 파일 | 없음 — 손대지 않으므로 2026년 숫자가 그대로다 |
| 새 파일의 파워쿼리 `Order_Book` | 새 파일 | 없음 — 아래 참고 |

### 새 파일의 파워쿼리 Order_Book

파워쿼리는 각 SO 라인을 **등록 Period부터 파일 안의 마지막 Period까지** 펼치고, 그룹별로
**이번 달 Start = 지난달 Ending**을 굴린다. 이월된 미출고 라인은 2026년 등록월에서 Input으로 시작해
Output 없이 `2027-01`까지 굴러오므로 **1월 Start = 2026년 12월 Ending**이 된다. 끝난 라인은 원래
Input − Output = 0이라 넘기지 않아도 합계가 같다.

- **2026년 Period 행은 이월분만의 부분 그림이다.** 피벗에서는 `Period ≥ 2027-01`만 본다.
- **SO 라인에 못 붙은 DN은 조용히 버려진다** (SQL은 `UNKNOWN`으로 드러내지만 파워쿼리는 아니다).
  이월 안 한 라인에 2027년 DN이 생기면 새 파일 Order_Book에 안 잡힌다. DN을 입력할 때
  `Item`·`Unit Price`가 `#N/A`로 뜨는 게 신호다 → 그 SO 라인을 새 파일로 복사하고 이월 목록에 추가한다.

## 실행 순서 (2027년 1월 중순)

1월 1일부터 전환 전까지의 입력은 **2026 파일에 계속** 한다. 이 기간에는 `create_dn P01`이
2026년 1월의 `Invoiced P01`과 섞일 수 있다 — 같은 SO가 2026년 1월과 2027년 1월 둘 다 계산서가
끊긴 경우(1년 넘게 걸친 주문)에만 해당해서 드물다. 그 달 미리보기를 한 번 더 본다.

1. 12월분 `세금계산서 발행일`(국내)과 `선적일`(해외)을 채운다. `create_dn P12`의 누락도 정리한다.
2. P12 대사: `reconcile_po.py P12`, `reconcile_so.py P12`, `reconcile_ind.py P12`
3. `close_period.py 2026-12`
4. **DB 백업 사본**: `noah_data.db` → `backup/noah_data_2026.db`
   (`sync_db.py`가 매번 WAL을 비우므로 파일 하나만 복사하면 된다)
5. 연말 측정 (아래 '실행 전에 셀 것')과 이월 목록 확정
6. 전환 — Excel COM으로 한다 (**openpyxl로 저장 금지**: 피벗 3개·파워쿼리 연결 14개가 사라진다)
   1. `NOAH_SO_PO_DN.xlsx` → `NOAH_SO_PO_DN_2026.xlsx`로 이름 변경. **이후 이 파일의 행은 지우지 않는다**
   2. 그 파일을 복사해서 `NOAH_SO_PO_DN.xlsx`를 만든다 (**빈 파일에서 시작하지 않는다** —
      파워쿼리·피벗·계산 열·XLOOKUP이 그대로 따라오게)
   3. 새 파일에서 넘기지 않는 행을 지운다. 함께 넘긴 2026년 `Invoiced` PO 행에 연도를 붙인다
   4. 이월 목록 CSV를 2026 파일 옆에 저장한다
7. `sync_db.py --dry-run` → **신규 0 / 삭제 0 / 수정 = 연도를 붙인 PO 행 수(Status만 바뀜)**.
   이월한 행은 키와 값이 그대로이므로 그 밖의 변화는 없어야 정상이다. 하나라도 나오면 원인을 찾는다.
8. 교차 확인 (DB): `ob_snapshot` 2026-12에서 Ending > 0인 그룹과 이월한 SO 라인을 대조한다.
   어긋나는 라인은 대개 'SO-DN 금액 불일치'(Ending ≠ 0) 진단 대상이니 하나씩 본다.
9. 교차 확인 (Excel): 두 파일의 파워쿼리를 새로고침하고
   **새 파일 `2027-01` Start 합계 = 2026 파일 `2026-12` Ending 합계 − 넘기지 않은 금액 불일치 라인 합계**.
10. 실제 `sync_db.py` 실행 → 대시보드 확인

## 실행 전에 셀 것 (연말 측정)

- 넘길 SO 라인 수 — (a) 12-31에 안 끝남 / (b) 2027 등록 / (c) 2027 DN, 그중 DN을 함께 끌고 가는 라인 수
- 연도를 붙여야 하는 `Invoiced` PO 행 수 (= dry-run의 예상 '수정' 건수)
- `Invoiced P01`이 2026년 1월 것인지 2027년 1월 것인지 — SO 등록월·DN 날짜로 가린다
- SO 라인 ↔ PO 행이 1:1이 아닌 경우 (예: PO가 부속을 한 라인에 합친 `SA09X-MA + ADAPTER`)
- SO 라인은 끝났는데 PO가 미정산인 행 (공장 미청구) — 넘길지 사람이 판단한다
- PO는 `Invoiced`인데 DN이 없는 라인 (`create_dn` 누락) — 전환 전에 해소한다
- 한 DN에 SO가 둘 이상 실린 경우 (DN 번호 재사용) — DN_ID가 두 파일로 갈려도 PK는 안 깨지지만 눈으로 확인한다

## 함정 체크리스트

- [ ] 2026 파일의 행은 지우지 않는다 (복사다). 이월 목록 없이 동기화하지 않는다
- [ ] **이월된 건은 2027 파일에서만 고친다** — 2026 파일에서 고쳐도 DB에 안 들어간다
- [ ] 분할 행 그룹은 통째로 넘긴다 (`_row_seq`)
- [ ] SO 수량을 잔량으로 고치지 않는다 (예외 ②)
- [ ] 옛 파일을 **DN 백업 폴더(`DN_BACKUP_DIR`)에 두지 않는다** — `dn_writer.backup_workbook`이
      `NOAH_SO_PO_DN_*.xlsx`를 오래된 순으로 지우는데, `_2026`은 이름순으로 가장 오래된 쪽에 선다
- [ ] 새 파일은 COM으로만 저장한다 (openpyxl 금지)
- [ ] 전환 전에 DB 백업 사본을 만든다
- [ ] `--dry-run`이 예상대로 나오기 전에는 실제 동기화를 돌리지 않는다
